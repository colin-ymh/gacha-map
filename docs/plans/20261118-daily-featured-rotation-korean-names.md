# 오늘의 가챠 노출 주기와 상품명

## Request

날짜가 바뀌어도 비슷한 상품이 보이는 빈도를 줄이고 홈의 오늘의 가챠에 일본어 원문 상품명이 표시되는 경로를 없앤다.

## Scope

- 오늘의 가챠 후보 선정과 날짜별 순환.
- 한국어 대표 상품명이 확인된 상품의 오늘의 가챠 노출.

## Out of Scope

- 상품 검색·상세의 전체 번역 또는 원문 데이터 정리.
- 개별 구성품의 번역 정책과 뽑기 이력, 홈 레이아웃.
- 앱이 열린 상태에서 KST 날짜가 바뀔 때 자동으로 목록을 갱신하는 동작. 2026-11-18 사용자 요청으로 작업 범위에서 제외했다.
- Collector의 별도 미배포 변경과 운영 데이터 재수집.

## Evidence

- 2026-11-18 07:35 KST 운영 API는 10건을 반환했다. 현재 목록에는 한국어명이 없거나 일본어 원문이 표시된 상품이 없었다. HTTP 캐시는 MISS였다. 과거 선정 이력 및 운영 RPC의 실제 버전은 현 세션에 Supabase 연결이 없어 확인하지 못했다.
- 저장소의 선정 규칙은 인기 슬롯에 최근 2일의 인기 노출만 반영하고 랜덤 슬롯에는 최근 7일의 전체 노출을 반영한다. 랜덤으로 노출된 상품은 다음 날 인기 슬롯에 들어갈 수 있다.
- 인기 점수는 최근 14일의 찜과 뽑기를 사용한다. 최소 2명의 반응이 있는 상품만 인기 후보이며, 부족한 인기 슬롯은 일반 후보가 채운다. 반응량이 원인인지 확인하려면 운영에서 날짜별 인기 슬롯 사용 수, 2인 이상 반응한 후보 수, 슬롯별 상품 재등장 빈도를 확인한다.
- 웹 API의 대표명 fallback은 `name_ko`가 null이면 `name_ja` 또는 `name`을 반환한다. 선정 단계에는 한국어 대표명 조건이 없다.
- 모바일 훅의 날짜 검사와 목록 요청은 마운트에만 연결되어 있다. 앱이 계속 켜져 있으면 KST 자정을 지나도 목록이 바뀌지 않을 수 있다.
- [Notion 뽑기 기획](https://app.notion.com/p/38c203d520db81b8959ffb27760bfffa)은 개별 구성품 이름의 기존 fallback을 설명한다. 오늘의 가챠 캐러셀의 전용 선정 기획은 찾지 못했다.

## Plan

1. 작업 가능한 Supabase 연결에서 live RPC 시그니처 및 최근 14일 일별 중복, 상위 3칸 중복, 인기 슬롯 사용 수, 찜과 뽑기 신호로 확보되는 후보 수, 한국어 이름 누락과 후보 풀 크기를 읽기 전용으로 측정한다.
2. 동의 후 기존 RPC 시그니처와 응답을 유지하는 교체 마이그레이션을 작성한다. 활성 이미지 요건에 더해 유효한 `name_ko`를 요구한다. Collector의 일본어 문자 검사를 기준으로 가나·한자 및 반각 가나 잔존을 제외한다. 영문 브랜드명은 허용한다.
3. 인기 슬롯과 랜덤 슬롯 모두 지난 7일의 **모든** 노출을 기준으로 최근 미노출 상품을 우선한다. 인기 슬롯은 적합한 인기 후보 중에서 점수순으로 최대 3개를 뽑고 부족한 칸은 최근 미노출 상품으로 채운다. 최근 미노출 후보가 10개에 못 미칠 때만 마지막 노출일이 오래된 상품부터 채운다.
4. 오늘 이미 저장된 목록은 유효한 상품과 순서를 유지한다. 오늘 목록에서 이름이나 이미지 조건을 충족하지 않는 상품만 다른 유효 후보로 보충한다. 기존 날짜별 잠금과 유일성 제약을 사용한다. 과거 날짜 조회와 이번 주 신상 중복 제외의 계약을 검증한다.

## Verification

- 오늘 날짜의 재요청은 같은 순서와 목록. 서로 다른 날짜는 충분한 신규 후보가 있을 때 최근 7일 노출 상품과 겹치지 않는다.
- 인기 후보가 모두 최근 노출되어도 후보가 충분하면 10칸을 채운다. 모자랄 때만 가장 오래된 노출부터 채운다.
- null, 공백, 가나·한자가 잔존하는 상품명 제외. 한국어와 영문 브랜드 예시는 포함.
- 오늘의 부적합 항목 교체 후 유효 항목의 상대 순서 유지. 저장 날짜의 동시 호출, 비로그인 호출, 과거 날짜 생성 금지, 이번 주 신상과 중복 제외를 확인한다.
- 첫 새 KST 날짜의 운영 목록 10개와 직전 7일의 전체 슬롯 중복 여부를 확인한다.

## Risks / Questions

- 운영 후보 풀과 최근 선정 이력이 확인되기 전에는 중복 감소량을 단정할 수 없다.
- 오늘의 일부 상품을 교체해도 이전 앱 버전이 저장한 당일 캐시는 그날의 재접속에서 그대로 보일 수 있다.
- RPC 마이그레이션 작성 및 dev 적용, 이후 운영 적용은 AGENTS.md의 사전 확인과 적용 순서를 따른다.

## Adversarial Review

- 인기 슬롯만 제한하면 랜덤에서 인기로 넘어오는 중복이 남는다. 모든 슬롯 이력을 한 번에 반영하고 순서를 강제한다.
- 번역되지 않은 상품을 API 응답에서만 제거하면 슬롯이 비거나 이번 주 신상에서 계속 제외된다. 선정과 오늘 목록 보충을 같은 RPC에서 처리한다.
- 매 요청마다 재선정하면 하루 안에 목록이 흔들린다. 조건을 잃은 오늘의 기존 항목만 날짜 잠금 하에서 교체한다.

## Final Plan

서버 선정 규칙을 적용하면 기존 앱에서도 새로 생성되는 목록부터 개선된다. DB 승인 후 dev에서 실측과 롤백 테스트를 진행하고, 운영 반영은 dev 검증 뒤 승인 범위에 맞춰 진행한다.

2026-11-18 사용자 승인 범위는 서버 선정 마이그레이션 작성 및 dev 검증이다. 신규 후보 선정은 직전 7일의 전체 슬롯 이력을 공유한다. 날짜별 기존 유효 행은 기존 rank를 보존하고, 오늘 비어 있는 rank만 채운다. 기본 10칸이 짧은 공개 RPC 호출로 고정되지 않게 저장 최소 목표를 10칸으로 두고 반환 수는 호출 인자로 제한한다. 기존 2인자 함수가 남아 있는 환경도 고려해 옛 오버로드를 정리한다. 연결된 Supabase 도구가 없으면 격리된 PostgreSQL에서 초기 스키마부터 회귀 SQL을 실행하고, dev 적용은 별도로 기록한다.
