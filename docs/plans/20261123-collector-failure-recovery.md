# 매장 Collector 연결 장애와 중단 복구 개선

## Request
카카오 한도 초과가 의심된 정기 수집 실패를 점검한 결과를 바탕으로, 장애가 전체 수집을 막거나 이미 얻은 결과를 잃지 않도록 개선한다. 설계 제시 뒤 사용자 `ㄱㄱ`로 구현 및 설명한 최소 DB·실행 설정 변경 진행 승인을 받았다. 자동 커밋은 하지 않고 검증 결과와 변경 범위를 먼저 보고한다.

## Scope
- 카카오·네이버 매장 수집의 오류 분류, 실행 시간/호출 예산, 수집원별 장애 격리.
- 검색 대상 단위 중간 저장, 성공 기록과 재개, 정상 0건 결과의 보존.
- GitHub 실행 환경 비교 진단과 정기 실행 구성 개선안.
- 누락·부분 성공·실패를 구분하는 결과 보고 및 회귀 검증.

## Out of Scope
- 인스타그램 운영 연결, 소비자 UI, 가격·실시간 재고 추정.
- 상품명 승인 기준 완화, 이번 미승인 상품 4개의 운영 데이터 수정.
- 유료 Google 수집 활성화, 신규 실행 서버/큐 서비스 도입, 무제한 재시도.
- 기존 매장 삭제·폐업 추정, 사업자/사용자 제보 덮어쓰기.

## Plan

### 1. 저장 없는 연결 진단
- 승인 후 수동 전용 진단 workflow를 추가한다. Supabase·OpenAI 키는 전달하지 않으며 DB에 연결하지 않는다.
- Ubuntu 24.04와 ubuntu-latest(실패 실행에서 26.04로 관측)에서 같은 Node 22로 DNS 조회, 인증 없는 curl/fetch 응답, 선택적으로 기존 카카오 키를 사용한 검색 1회를 비교한다. 실제 이미지 버전도 보고하며 공개 runner label로 확인되지 않은 26.04 고정 label을 가정하지 않는다. 총 호출 수와 실행 시간은 작게 고정한다.
- 실행 이미지·지역·목적지 IP·HTTP 상태·공급자 오류 코드·소요 시간을 기록한다. 키, Authorization, 인증 환경, 검색 결과 원문은 기록하지 않는다.
- 반복 가능한 최소 비교까지만 진행한다. OS별 실행 지역이 같지 않으면 결과를 환경 차이로만 해석한다. 인증 없는 연결은 되는데 인증 호출만 실패하면 키·권한·한도 문제를 별도로 구분한다.
- 24.04에서만 안정적이라는 근거가 얻어지면 당분간 버전을 고정한다. 지역 고정은 이 설정으로 보장할 수 없으며, 버전 고정만으로 복구 완료로 처리하지 않는다.

### 2. 공통 요청 처리와 오류별 중단
기존 TypeScript 수집기에 작은 요청 보조 함수를 추가한다. 새 프레임워크는 도입하지 않는다.

| 관측한 오류 | 처리 |
| --- | --- |
| 한도 초과 코드(-10 등) | 해당 공급자 즉시 중단, quota_limited 보고. 리셋 시각을 임의로 가정하지 않는다. |
| 429 | 공급자 코드/Retry-After로 분류. 짧고 명확한 대기만 1회 허용하고, 모호하거나 예산 초과면 보류한다. |
| 401/403 | 인증·권한 오류로 즉시 중단. 다른 수집원은 계속하되 전체 실행을 정상으로 표시하지 않는다. |
| DNS/연결/요청 시간 초과, 5xx | 최초 포함 최대 2회 시도, 지수 대기와 작은 지터 적용. 연속 3개 대상 실패 시 공급자 회로 차단. |
| 잘못된 JSON/응답 계약 | 성공 0건으로 변환하지 않고 계약 오류로 중단·보고. |
| DB 저장/체크포인트 실패 | 해당 수집 job을 즉시 중단하고 공통 후속 쓰기를 금지한다. 부분 성공 옵션으로 숨기지 않는다. |

- 초기 제안값: 요청 전체(본문 포함) 10초, 네트워크 연속 실패 3개 대상, 공급자별 소프트 예산 45분. 네트워크 완전 단절은 약 1~2분 안에 차단되는지 검증한다.
- 재시도와 페이지네이션도 호출 예산에 포함한다. 공급자별 요청 간격을 유지하며 병렬 호출을 늘리는 방식으로 속도를 해결하지 않는다.
- 카카오 기본/보충은 같은 공급자 회로 상태를 공유해 기본 수집 차단 뒤 보충 520건을 다시 시도하지 않는다.
- 숫자는 초기 운영값이며 표본 실행 결과로 조정한다. 45분을 넘는 정상 분량은 성공으로 간주하지 않고 남은 대상으로 재개한다.

### 3. 대상별 저장과 재개
- 검색 대상 하나가 완료될 때마다 raw_places를 기존 source+external_id 기준으로 중복 방지 저장한다. 수천 검색의 전체 결과를 메모리에 쌓지 않는다.
- raw 저장 성공 뒤에만 해당 검색의 collection_runs success를 기록한다. 정상 0건도 success/result_count=0을 기록한다.
- raw 저장 성공 후 기록 저장이 실패하면 다음 실행에서 다시 조회될 수 있지만 중복 저장으로 복구 가능하다. 순서를 뒤집어 영구 누락시키지 않는다.
- 진행 중인 대상의 여러 페이지는 하나의 완료 단위다. 일부 페이지만 받았거나 중단된 대상을 완료로 기록하지 않는다. 이전에 완료된 대상은 보존한다.
- supplement-pilot뿐 아니라 standard에서도 기록을 남긴다. 실행 ID와 phase/region/cell/query/family/mode를 포함한 기존 targetKey로 재개한다.
- raw_places의 출처만으로는 전체 검색 완료를 증명하지 못하므로 재개 판단에서 제외한다. collection_runs의 저장 완료 기록을 사용한다. 첫 전환 시 standard 대상은 한 번 추가 조회될 수 있다.
- 네이버를 같은 계약으로 처리하기 위해 기존 collection_runs의 source 제약에 naver를 허용하는 최소 migration을 제안한다. 새 테이블/상태 체계는 우선 추가하지 않는다.
- 필요한 기간의 기록만 조회하고 페이지 순서를 안정화한다. 기존 인덱스로 충분한지는 실제 조회 계획을 확인한 뒤 결정한다.

### 4. 수집원별 실행 분리와 최종 판정
- 하나의 workflow 안에서 준비 → 카카오/네이버 별도 job → 공통 정제·검수·승격 → 최종 보고 순서로 구성한다.
- 준비 단계에서 기존 후보 범위 기준을 한 번 확보하고, 쓰기 실행 간 중복 방지 동시성 규칙을 유지한다.
- 카카오·네이버는 저장소의 source 키로 구분되므로 각자 raw 저장만 수행한다. 정제·그룹화·승격은 두 수집 job이 종료된 뒤 한 번만 실행한다.
- 공급자 일부 장애이고 저장된 입력의 계약이 유효하면 성공한 데이터의 후속 처리를 진행한다. source 실패가 누락돼 운영자가 전체 성공으로 오인하지 않도록 마지막 집계는 실패/부분 완료를 명시한다.
- 두 수집원이 모두 실패하거나 DB/데이터 계약 오류가 있으면 승격을 막는다. 정상적인 신규 결과 0건은 장애와 구분한다.
- 단순 continue-on-error/무조건 always만으로 후속 쓰기를 열지 않는다. 각 job의 명시적 결과 보고와 DB 오류 여부를 함께 판단한다.
- 공급자 소프트 예산보다 여유 있는 job 제한(초기 60분)을 두고, 종료 전 보고/파일 업로드 시간을 확보한다. 정제 단계는 기존 정상 소요를 기준으로 별도 제한한다.

### 5. 운영 결과를 한눈에 확인
- 수집원별 planned/completed/failed/not_attempted, 정상 0건, 실제 HTTP 시도 수, raw 저장 시도/확인 건수, 소요 시간, 회로 차단 이유를 기록한다.
- raw 저장 시도 건수를 신규 매장 수로 표시하지 않는다. 최종 매장 추가/갱신은 승격 결과에서 따로 집계한다.
- 중복 충돌 무시 건수를 정확히 알 수 없으면 신규 삽입 건수로 추정하지 않는다.
- 키/Authorization·민감한 원문을 제외한 요약과 제한된 오류 표본만 GitHub Summary와 artifact로 남긴다.
- 실패 알림에 원인·보존 범위·미시도 대상·재개 방법을 포함한다. 자동 복구 재실행은 최초에는 활성화하지 않고 멱등성 검증 후 결정한다.

## Verification
- DNS 실패/10초 시간 초과가 반복돼도 전체 1,920건을 실행하지 않고 공급자 차단. 카카오 보충도 재호출하지 않으며 네이버는 독립적으로 실행.
- -10, 401/403은 즉시 중단, 429/5xx 재시도는 최대 횟수·대기·전체 예산을 준수. 오류 본문이 로그에 키를 반사해도 노출되지 않도록 정제.
- 완료 대상 A 후 B 실행 중 종료 → A의 raw/완료 기록 보존, 재개 시 B부터 대상 선정. A가 정상 0건이어도 재조회하지 않음.
- raw 저장 실패/완료 기록 실패 각각 주입: 실패를 보고하고 성공 기록으로 건너뛰지 않음. 재실행 시 중복/영구 누락 없음.
- 모든 결과가 기존 장소 중복이어도 검색 대상의 성공 기록은 남음. 기존 new-only 의미와 source 구분을 유지.
- 정기·수동 실행이 겹쳐도 공통 후처리/승격을 동시 실행하지 않음. 저장소 중복 방지와 기록 기반 재개를 별도 검증.
- 한 수집원 실패/양쪽 실패/정상 0건/DB 장애에서 후속 실행과 최종 상태가 의도대로 동작.
- Collector 기존 테스트, 변경 경로 타입 검사, 요청/재개/보고 회귀 테스트, workflow 구문/조건 검증.
- migration은 승인 후 dev 적용 → 실제 표본/제약 검사 → prod 적용·검증 순서. 공급자 비교 진단과 작은 표본 수집에서 성공 기록 확인 후 전체 정기 실행을 재개.
- 성공 기준: 연결 단절이 수시간 실행으로 번지지 않음, 완료된 검색 결과 보존, 실패·0건 구분, 다음 실행에서 미완료 대상 복구, 건강한 수집원의 결과는 정상 후처리.

## Risks / Questions
- GitHub 이미지·네트워크 환경 차이는 현재 가설이며, 카카오 서버/경로/출발지 제한 중 어느 지점이 원인인지는 기존 로그만으로 확정할 수 없다.
- 로컬 키의 현재 성공은 GitHub 키의 동일성이나 실패 당시 쿼터를 증명하지 않는다. 관리자 통계는 로그인 후 별도 확인이 필요하다.
- 검색당 저장/기록으로 DB 요청 수가 늘어난다. API 비용을 줄이는 완료 기록의 이점과 비교하고, 실제 지연이 유의미할 때만 작은 묶음 저장을 검토한다.
- raw_places 기록과 collection_runs 기록은 별도 트랜잭션이다. 멱등 재시도로 안전하게 처리하며, 초기부터 새 RPC를 추가하지 않는다.
- collection_runs의 naver 제약 변경과 GitHub workflow/실행 환경 변경은 설명 후 사용자 `ㄱㄱ`로 진행 승인을 받았다. 커밋·푸시는 변경 보고 후 별도 지시를 따른다.
- 인스타그램 및 다른 세션의 미커밋 작업은 보존한다. 계획의 SQL/코드를 기존 작업과 섞어서 커밋하지 않는다.

## Adversarial Review
- OS 고정만 하면 재발하지 않는가? 보장할 수 없다. 환경 비교와 오류 격리·중간 저장을 독립적으로 수행한다.
- allow-partial을 유지하면 전체 실패가 성공으로 숨겨지는가? 공급자 결과는 보존하고 마지막 집계에서 실패를 유지한다. DB 장애가 난 job은 즉시 중단하고 후속 정제·승격도 막는다. 이미 실행 중인 다른 수집 job의 raw 저장을 즉시 취소할 수 있다고 가정하지 않는다.
- 기록을 먼저 쓰면 저장 실패 때 검색을 영원히 건너뛰지 않는가? raw 저장 이후에만 success 기록을 남긴다.
- 0건과 1페이지 부분 수신은 같은가? 정상 종료한 전체 검색만 success로 기록한다.
- 네이버를 기존 실행 기록에 그냥 쓰면 되는가? 운영 제약이 거부한다. 최소 migration과 dev→prod 검증을 필수 의존성으로 둔다.
- 실패 시 같은 API를 다시 여러 job에서 호출하지 않는가? 카카오 기본/보충을 같은 공급자 job과 회로로 묶고 실제 호출 수 예산을 공유한다.
- 병렬화가 판정·승격을 경합시키지 않는가? 병렬 범위는 공급자 raw 수집까지만이며 후처리는 단일 단계다.
- 저장 시도 3천건을 새 매장 3천개라고 오인하지 않는가? 입력·저장 확인·신규 승격을 분리해 보고한다.

## Final Plan

2. 요청 오류 분류·제한된 재시도·카카오 공급자 회로·검색 대상별 raw 저장을 먼저 구현·검증한다.

4. 승인 후 dev→prod 제약 검증과 수집원 job 분리·진단 실행을 진행한다. 결과에 근거해 실행 이미지 고정 여부를 결정한다.

문서 검토 결과: 기존 구조를 활용하는 개선으로 실행 가능하다. 최소 DB·실행 설정 변경 승인을 받았다. 운영 적용 완료 판정에는 실제 중단·재개 검증과 GitHub에서의 비교 진단이 필요하다. 커밋·푸시는 변경 보고 후 별도 지시를 따른다.
