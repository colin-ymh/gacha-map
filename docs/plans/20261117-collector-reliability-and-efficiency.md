# Gacha Collector 수집 품질 및 효율 개선

## Request

상품과 매장 수집 검토에서 확인한 한국어명 승인 누락, Tarlin 중복 조회, 매장 발굴·상태 확인, 제조사 수집 누락, 구성품 재수집 안전성을 개선한다.

## Scope

- 기존 사전 조합 후보를 신뢰도와 품질 검사에 따라 승인하고 보류 사유를 남긴다.
- Tarlin 목록에서 기존 상품을 제외한 뒤 상세를 조회한다.
- 매장 발굴의 출처와 검색어·지역별 승격 근거를 보고하고, 기존 폐업·주소 변경 제보를 상태 점검에 연결한다.
- 제조사별 목록·상세 실패를 보고하고 부분 성공을 저장한다. 월별 검토 일정에 조회량을 제한한 누락 탐색을 추가한다.
- 승인 후 상품 수집 실패를 다음 실행에서 재시도할 수 있게 저장하고, 구성품을 한 트랜잭션에서 ID와 번역을 보존하며 갱신한다.

## Out of Scope

- UI, 검색 API 응답, 택소노미 v2 적용, 제조사 추가, 과거 카탈로그 전체 재수집.
- 유료 매장 API 확대, 제보 기반 무검수 폐업 처리, 배포·커밋.

## Relevant Files

- Collector의 `.github/workflows/biweekly-collector.yml`, `scripts/approve-gacha-product-name-candidates.ts`, `scripts/collect-gacha-products.ts`, `scripts/check-shop-status.ts`, `scripts/report-biweekly-collector.ts`.
- Gacha Map의 `supabase/migrations/`, `supabase/tests/`, `apps/web/src/app/api/admin/reports/`, 상품 구성품·뽑기 API.

## Plan

1. 현재 동작, 기존 작업 diff, 운영 테이블·제약과 배치 로그를 확인한다. 작업을 한국어명, 상품 수집, 매장 운영, DB 계약으로 나눈다.
2. 승인 배치에 `name_parts` 후보를 포함한다. `name_parts:v1` 사전 조합만 추가 허용하고 상품당 한 후보를 선택한다. 보류 사유와 표본은 기존 배치 보고서에 노출한다.
3. Tarlin을 포함한 상세 수집에서 실패를 개별 기록한다. 실패한 제조사가 다른 제조사 수집과 성공 데이터 저장을 막지 않도록 하고, 소스별 보고서와 Actions 경고를 남긴다. 월간 누락 탐색은 정상 경로에 한정해 페이지와 상품 수를 제한한다.
4. 매장 배치에 실제 상태 조회, 미실행, 제보 검수 수치를 추가한다. 신규 승격 그룹에 연결된 원본의 출처·지역·검색어를 집계하고 실행 횟수와 대조한다. 관측이 쌓일 때까지 기존 전국 검색 범위를 유지한다.
5. DB 작업 확인 후 상품 수집 실패 항목과 재시도 시각·횟수를 관리한다. 구성품용 서비스 역할 RPC는 같은 상품의 쓰기를 직렬화하고 안정적으로 식별한 기존 행을 갱신한다. 불명확한 대응은 보류하고 뽑기 이력의 참조 대상은 보존한다. 추출 상태와 구성품 저장을 함께 커밋한다.

## Verification

- 한국어명 승인에서 사전 후보만 새로 선택되고, 보류 후보·기존 대표명·중복 상품이 안전하게 처리되는지 확인한다.
- Tarlin 모의 목록·상세 호출에서 기존 ID 상세 호출 0건, 중복 ID 1회, 신규 한도, 한 상세 실패 후 후속 저장을 검증한다.
- 제조사별 정상 0건·HTTP 오류·파싱 오류와 월간 탐색 한도를 검증한다. 상품 배치 dry run은 승인이나 DB 쓰기를 수행하지 않는다.
- 매장 상태 점검에서 Google 키 없음·조회 실패·정상 확인을 구분한다. 기존 제보의 개인정보를 배치 산출물에 포함하지 않는다. 승격 귀속은 최초 저장된 원본의 검색 근거임을 명시한다.
- 승인된 DB 변경은 dev부터 검증한다. 동일 입력 재실행, 순서 변경, 기존 한국어명과 뽑기 참조 보존, 빈 추출, 실패 롤백, 동시 실행, 재시도 한도와 권한을 검증한다.
- Collector 테스트, 타입 검사 진단 비교, 워크플로 문법, 두 저장소의 diff를 확인한다.

## Risks / Questions

- Collector는 쓰기 허용 경로 밖에 있으며, 실제 적용에는 해당 경로에 대한 도구 승인이 필요하다.
- DB 마이그레이션 작성·적용은 사전 확인 대상이다. 적용이 승인되면 dev → 검증 → prod 순서로 진행한다.
- 택소노미 v2 Collector 작업본은 기존 로컬 변경이다. 이 작업의 검증 및 배포 범위와 섞지 않는다.

## Adversarial Review

- 신뢰도만으로 승인하면 음차·수동 검수 후보까지 섞인다. 사전 후보의 출처와 버전을 제한하고 기존 용어 및 일본어 잔존 검사도 유지한다.
- 같은 상품의 여러 후보를 RPC에 보내면 나중 후보가 대표명을 바꿀 수 있다. 검사를 통과한 후보 중 사전 조합을 우선하고 상품당 한 건만 승인한다.
- 정상 0건과 빈 HTML 구조는 단일 응답으로 구별하기 어렵다. HTTP 및 상세 파싱 오류는 별도 기록하고, 0건은 목록 종료 근거와 함께 남긴다.
- 월간 백필은 기존 키 뒤에 숨은 상품을 발견해야 한다. 고정된 상한에서 운영 부하를 관찰하며 과거 전체 누락의 해결 여부를 별도로 판정한다.
- 원본 한 곳이 여러 검색어에서 발견되면 첫 원본의 검색어만으로 전체 기여도를 판단할 수 없다. 관측 신호를 제공하고 자동 중단에는 사용하지 않는다.
- 구성품 이름·위치가 바뀌거나 이미지가 재사용될 수 있다. 명확한 1:1 근거가 없는 경우 기존 ID를 다른 구성품에 연결하지 않는다.
- 운영의 뽑기 기록은 구성품 ID에 삭제 제한 외래 키를 둔다. 은퇴한 행은 현행 RLS 때문에 일부 뽑기 조회에서 메타데이터가 빠질 수 있다. 이번 마이그레이션 범위는 안전한 추가·갱신으로 제한하고, 자동 삭제·은퇴를 사용하지 않는다.
- 예전 `source_variant_key`에는 표시 순서가 들어간다. 원문명·개별 이미지가 기존·신규 양쪽에서 유일하고 서로 모순되지 않을 때만 기존 ID를 이어 쓴다. 순번 변경은 dev·운영의 실제 유일성 제약을 확인하고 충돌 없는 임시 순번을 검증한다.
- 원천 상품 키 저장 후 구성품 저장이 실패하면 일반 신규 필터가 다음 실행에서 건너뛴다. 재시도 큐는 목록·상세·파싱·저장 실패를 별도로 관리하며, 알려진 원천 키라도 저장 실패를 복구할 수 있게 한다. 출시 월 변경과 별개로 실패한 상품만 다시 처리한다.
- 구성품 쓰기는 공식 상품 수집, 구성품 전용 재추출, Tarlin OCR 경로를 함께 확인한다. 기존 한국어명·영문명·수동 수정·OCR 근거를 보존하고, 번역 도중 원문이 바뀐 경우 이전 원문으로 생성한 번역을 쓰지 않는다.

## Final Plan

1. 기존 DB 계약을 활용하는 승인 경로, Tarlin 증분 상세, 실패 분류, 제한된 월간 탐색, 매장 상태와 승격 보고부터 구현·검증한다.
2. 안정 저장과 장기 재시도는 운영 제약에 맞는 마이그레이션 범위로 검토하여 사전 확인을 받은 뒤 진행한다.
3. 승인받은 적용 범위만 반영한다. 실행 로그와 운영 데이터에서 수집량·승격량·한국어명 반영률을 다시 확인하기 전까지 해당 운영 효과는 예상으로 기록한다.

## DB 승인 이후 상세 순서

1. dev·운영의 구성품 및 원천 키 제약, 조회 권한, 저장 경로를 대조한다. 실패 키는 출처·단계·공식 URL 단위로 중복을 제한하며 마지막 오류, 시도 횟수와 다음 시도 시각을 갖는다. 영구 오류와 재시도 한도 초과는 보고서에 남긴다.
2. 구성품 RPC는 상품 행을 잠근 뒤 매칭과 순번을 계산하고, 구성품 및 추출 상태를 함께 갱신한다. 불완전한 추출과 모호한 항목은 기존 라인업을 유지하고 검토 사유를 남긴다.
3. Collector는 재시도 대상의 공식 출처를 기존 어댑터 allowlist와 대조한다. 정기 실행에서 제조사별 재시도 상한과 backoff를 적용하고, 성공적으로 저장된 작업만 완료 처리한다. 읽기 전용 모드에서 큐를 수정하지 않는다.
4. 승인된 범위에 맞춰 dev에서 SQL 롤백 테스트와 수집 스크립트 재실행을 검증한다. 운영 적용이 승인된 경우에만 prod 적용 및 검증을 진행한다.

## 코드 단계 결과

- Collector 작업 디렉터리에 승인, Tarlin 증분 상세, 제조사별 실패 보고, 매장 제보 및 승격 보고를 반영했다. 기존 택소노미 변경과 대상 파일이 겹치지 않는다.
- 상품 월간 탐색은 기존 첫 주 실행 조건에서 목록의 첫 8페이지까지 알려진 상품 페이지를 넘어간다. 빈 페이지와 요청 실패는 탐색을 종료한다.
- Collector 로컬 테스트 20개 파일, 173개 통과. 워크플로 YAML 파싱 및 Bash 구문 검사, Git diff 검사 통과. 전체 타입 검사는 기존 진단 21건으로 실패했고 신규 진단은 없다.
- 운영 DB 읽기 전용 확인에서 승인 후보의 상품 FK와 상태 제보 조회 컬럼이 있음을 확인했다. 변경 배치의 운영 실행, 배포, DB 마이그레이션은 수행하지 않았다.

## Dev DB 단계 결과

- 사용자 승인 범위는 마이그레이션 작성과 dev 적용·검증이다. 운영 적용 및 Collector 배포는 배포 단계에서 진행한다.
- `202611170001_collector_variant_writes.sql`은 원자적 라인업 저장 및 추출 결과 RPC, 원문·기존 번역을 확인하는 한국어명 저장 RPC를 추가한다. 공식 수집·구성품 전용 수집·Tarlin OpenAI OCR·Vision OCR에 연결했다. 기존 행의 삭제와 상태 변경 없이 매칭된 구성품의 ID·번역·기존 메타데이터를 보존한다.
- `202611170002_collector_retry_queue.sql`은 상품·구성품을 나눠 실패를 저장한다. 정기 실행당 제조사별 최대 5건을 선점하고, 작업별 최대 5회까지 재시도한다. 2시간 임대와 토큰 확인으로 이전 실행이 새 작업 결과를 덮어쓰지 못하게 한다.
- dev Supabase MCP로 두 마이그레이션을 적용했다. MCP 이력의 이름은 `collector_variant_writes` 및 `collector_retry_queue`이다. 롤백 기반 dev 회귀 SQL 두 건이 통과했다.
- dev의 별도 세션에서 같은 상품의 행 잠금을 잡은 동안 구성품 RPC가 대기하는 것을 확인했다. 양쪽 트랜잭션을 롤백했다. Collector 작업 디렉터리의 테스트 20개 파일, 175개와 워크플로 구문 검사가 통과했다. 전체 타입 검사의 기존 오류 21건에 신규 진단은 없다.
- 운영 적용 순서는 두 마이그레이션 적용 → 기존 계약 및 권한 확인 → Collector 배포 → 다음 정기 실행과 리포트 검증이다.
