# 사업자 등록에서 기존 샵 찾기

## Request
사업자가 신규 등록 폼에 샵 이름을 입력하면 가챠맵에 있는 유사한 샵을 보여준다. 같은 샵이면 해당 샵의 소유권을 신청하고, 다른 지점이거나 검색 결과가 없으면 신규 등록을 계속한다.

## Scope
- 모바일·웹의 사업자 신규 등록 이름 필드 아래에 후보 목록을 제공한다.
- 기존에 등록된 활성 샵의 이름과 주소를 표시하고 소유권 신청 가능 여부를 구분한다.
- 샵 상세의 ‘이 샵의 사업자입니다’ 진입이 쓰는 `POST /api/shop-applications`를 재사용한다. 후보 선택 후 기존 `type: "claim_shop"`, `shop_id: 선택한 샵 ID` 계약으로 제출한다. 제안된 샵을 선택하는 행위는 신청서의 대상만 결정한다.

## Out of Scope
- 자동 소유권 연결, 샵 병합 및 기존 데이터 대량 수정.
- 이름 유사도만으로 신규 제출 차단, 반경만으로 기존 샵 자동 선택.
- 카카오 로컬에서 새 샵 후보 수집, 운영 DB 마이그레이션 적용.

## Relevant Files
- Notion 「사업자 샵 등록 기획」과 Penpot 신규 등록·소유권 신청 화면.
- `apps/mobile/app/shop-application.tsx`, `apps/web/src/components/organisms/shop-application/shop-application-form{,.view}.tsx`
- `apps/web/src/app/api/shops/route.ts`, `apps/web/src/app/api/shop-applications/route.ts`, `docs/api-contracts.md`
- 기존 샵 상세의 `/shop-application?shopId=…` 진입과 관리자 승인 RPC.

## Plan
1. **동작 사양** — 신규 등록에서 이름이 두 글자 이상이고 한글 조합이 끝난 뒤 약 300ms 기다려 조회한다. 이름 필드 아래에 최대 5개를 보여주며, 행에는 샵명과 도로명주소 또는 지역을 표시한다. 같은 이름의 지점을 주소로 구분한다.
2. **선택** — 소유권 신청이 가능한 샵을 누르면 선택한 이름·주소를 확인한 뒤 기존 `claim_shop` 폼으로 전환한다. 사업자번호·대표자·전화번호 등 공통 입력값은 화면 메모리에 유지한다. 신규 전용 주소·좌표는 claim 제출에 포함하지 않는다. 첨부는 재업로드와 이중 저장 없이 같은 폼 상태에서 관리한다. 전환 취소 시 신규 작성 상태를 복원한다.
3. **그대로 신규 등록** — 후보가 다르거나 없으면 입력을 계속한다. 이미 사업자가 연결된 후보는 상태를 명시하고 선택을 막는다. 검색 실패는 결과 없음과 구분하며, 재시도와 신규 등록 계속을 제공한다. 심사 중인 신청과 조회 후 소유권 상태가 바뀐 경우는 기존 제출 API 검증과 오류 문구를 사용한다.
4. **후보 조회** — 인증된 사업자 신청 전용 읽기 경로로 최대 5개의 `id`, `name`, `address`, `claimable`을 반환한다. 기존 샵 이름 조회 로직 중 재사용 가능한 부분을 확인한다. 지역 지오코딩 fallback과 일반 인기 정렬 없이, 정규화한 이름 완전 일치 → 접두·부분 일치 → 검증된 유사도 순으로 랭킹한다. 소유자 ID, 전화번호, 신청 정보는 응답에 포함하지 않는다. 최초에는 확장·인덱스 변경을 피하고, 짧은 한국어 이름·오타를 기존 검색으로 다룰 수 없는 경우에만 DB 변경 계획을 따로 검토한다.
5. **상태** — 중복 호출을 줄이고 이전 요청은 취소한다. 느린 응답이 최신 후보를 덮거나, 사용자가 기존 샵을 선택한 뒤 응답으로 선택이 바뀌지 않게 한다. 웹·모바일의 문구와 상태 정의는 공용으로 맞추고, UI는 각 플랫폼의 기존 폼 패턴을 따른다.

## Verification
- 정확 일치, 띄어쓰기·대소문자, 한글 오타와 짧은 이름, 동일 상호 다른 지점, 이미 연결된 샵, 결과 없음, 요청 실패와 느린 응답을 확인한다.
- 기존 샵 선택 → 확인 → `claim_shop` 제출 → 기존 관리자 승인 경로, 그리고 후보가 달라 신규 등록을 계속하는 흐름을 dev에서 확인한다.
- 후보 표시 후 타인이 소유권을 얻는 경우, 이미 자신의 신청이 심사 중인 경우, 전환 취소 및 폼 입력·첨부 보존을 확인한다.
- 후보 API 인증·응답 최소화·최대 건수를 테스트하고, 웹·모바일 타입 검사 및 브라우저·아이폰 상호작용을 검증한다.

## Risks / Questions
- 유사한 이름의 다른 지점이 많다. 주소를 함께 표시하고 사용자가 확인하도록 한다.
- 현재 일반 샵 검색은 이름 외 결과와 지역 fallback이 들어갈 수 있다. 신청 후보는 이름 중심으로 분리 검증한다.
- 이 플로우는 중복 등록 가능성을 줄이지만 동시에 제출된 신규 등록이나 기존 중복 데이터는 해결하지 않는다. 서버 중복 제약은 운영 데이터를 검토한 뒤 별도 결정한다.

## Adversarial Review
- 후보에서 선택한 ID와 폼 작성자의 증빙은 서버가 계속 검증해야 한다. 클라이언트의 `claimable`은 표시 시점의 안내다.
- 주소가 아직 입력되지 않은 단계에서 위치 일치로 잘못 판단할 수 있다. 범용 상호는 짧은 후보 목록에 주소를 병기하고 선택을 강제하지 않는다.
- 이름 검색 결과가 빈 경우와 네트워크 실패를 동일하게 처리하면 중복이 늘어난다. 구분된 상태를 사용한다.
- 라우트를 단순 교체하면 입력 및 첨부가 사라질 수 있다. 같은 폼에서 전환하고, 기존 샵 상세에서 직접 들어온 신청은 기존 진입을 그대로 쓴다.

## Final Plan
Notion에 신규 이름 입력 → 후보 → 기존 샵 확인/신규 계속 상태를 확정하고 Penpot에서 모바일과 웹을 확인한 뒤 구현한다. 후보 조회만 추가하고, 샵 상세와 신규 등록에서 전환한 신청 모두 기존 제출 API와 관리자 승인 경로를 공유한다. 이름 유사도 때문에 DB 변경이 필요하면 dev 검증 계획과 승인을 별도 진행한다.

## Implementation and verification
- Notion 진입 흐름과 Penpot 모바일·웹 후보 및 선택 후 확인 보드를 갱신했다.
- 인증된 이름 후보 GET과 공용 디바운스 훅을 추가했다. 기존 샵 신청 제출·승인 API와 DB 스키마는 그대로 사용한다.
- dev DB의 활성 샵과 소유 여부 조회를 읽기 전용으로 확인했다. API 테스트에서 인증, 길이 제한, 정렬·중복 제거·최대 5개, 소유자 ID 비노출을 확인했다.
- 웹 폼 테스트에서 이미 연결된 후보 차단, 기존 샵 선택·취소, 입력과 첨부 보존, 기존 claim 엔드포인트로의 multipart 제출을 확인했다. 로그인한 dev 사용자 제출·승인과 아이폰 화면은 미검증이다.
