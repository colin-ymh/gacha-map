# 탐색·검색 공용 상품 분류 개선

## Request
- 사용자가 자주 찾는 상품을 쉽게 발견하도록 gacha-map과 gacha-collector를 함께 개선한다.
- 카테고리 탐색과 검색 엔진이 같은 정규 분류를 사용해야 한다.

## Scope
- collector 추출에서 IP/브랜드와 제품 계열을 분리한다.
- 기존 명칭/승인 별칭을 정규 ID에 연결하며, 새 이름과 모호한 이름은 검토 후보로 남긴다.
- 분류 확정 결과를 검색 문서에 반영하고, 분류/별칭 변경 시 검색 문서 갱신 누락을 방지한다.
- 분류 갱신 실패를 성공처럼 처리하지 않는다. 대표 사례와 회귀 테스트를 추가한다.
- 각 환경의 기존 데이터를 독립적으로 검증한다. dev 데이터를 운영에 덮어쓰지 않는다.

## Out of Scope
- 전면 카테고리 트리 개편, 신규 검색 서비스 도입, 인기 수치 추정, 자동 대량 병합/삭제.
- 승인 없는 DB 변경/재분류 및 유료 LLM 일괄 실행.
- 화면 배치 변경은 별도 Notion/Penpot 확인 이후로 둔다. 이번 데이터 개선은 기존 탐색 UI에 제공한다.

## Relevant Files
- collector: scripts/decompose-gacha-product-names.ts, scripts/classify-gacha-series.ts, scripts/lib/gacha-product-{series,categories}.ts, scripts/lib/gacha-browse-views.ts
- map: supabase/migrations/, docs/api-contracts.md, packages/shared/src/types/index.ts
- Notion: 3c4203d520db81b4bfc7edb79627a3b4 (탐색), 373203d520db811b85dcee9729af857f (검색)

## Plan
1. 기존 추출·정규화·검색 문서 계약과 실제 DB 함수/권한/갱신 경로 확인.
2. 읽기 전용 DB 사전을 collector에서 조회한다. 정규 시리즈/카테고리와 승인 별칭을 기준으로 해석한다.
3. 추출 결과에 제품 계열 및 복수 시리즈 후보를 별도로 보관한다. 명칭 조합용 legacy 필드와 정규 분류 결과를 구분한다. 미확정 시리즈는 자동 active 생성하지 않는다.
4. DB 변경안 확인 후 마이그레이션 작성: 새 추출 버전의 확정 ID를 매핑하고 기존 수동 매핑은 보존한다. legacy 상품은 호환 경로 유지.
5. 확정된 시리즈/카테고리 및 승인 별칭을 기존 검색 doc_series/doc_all에 포함한다. 상품명/코드의 높은 우선순위와 토큰 AND를 보존한다. 자유 태그는 정규 카테고리가 되지 않는다.
6. 검색 dirty 큐가 관계/정규 명칭/별칭 변경을 추적하도록 한다. collector는 변경 상품을 명시적으로 갱신하고 실패를 보고한다.
7. 테스트·dev 검증 후 운영 적용 승인을 받은 범위만 적용한다. 실제 검색 결과와 탐색 결과를 교차 검증한다.

## Verification
- 명칭 예: 치이카와+메지루시, 무민+푸티또, 마치보케 단독, 라인+신규 IP, 헌터×헌터, 복수 IP 콜라보, Latin 브랜드, 모호한 별칭.
- 승인 별칭 검색, 다중 토큰 AND, 일반 상품명/코드 검색, inactive 항목 배제, 수동 연결 보존.
- 잘못된/중복 ID, 사전 변경, 빈 배열, 반복 refresh, legacy 호환성, RPC 누락/실패.
- 검색 색인 갱신 후 canonical/alias 결과 포함과 stale 항목 제거. 성능은 대표 질의 EXPLAIN으로 확인.
- collector 단위 테스트/타입 검사 및 변경 워크스페이스 검증. 기존 실패와 신규 실패를 구분한다.

## Risks / Questions
- DB 함수/스키마/마이그레이션은 AGENTS.md에 따라 사전 확인 필요. dev → 검증 → prod 순서.
- collector 경로가 현재 쓰기 허용 루트 밖이므로 실제 파일 수정 시 호스트 권한 승인 필요.
- unknown/other의 규모는 오류율이 아니다. 검증 없이 전체 재분류하지 않는다.
- 제품 수가 많다는 이유로 인기라고 판단하지 않는다. 검색/찜 등 실제 수요 로그와 큐레이션 정책은 후속으로 연결한다.
- `origin`의 국가/브랜드 혼재는 자동 이관하지 않고 현재 비노출 유지.

## Adversarial Review
- 프롬프트만 바꾸면 기존 active 생성 RPC가 파편을 재생성한다 → 새 추출 버전과 DB 소비자를 함께 검증한다.
- 새 IP를 null로만 버리면 검색·검토에서 소실된다 → 원문 후보를 JSON에 보존하고 명칭 검색 유지.
- collector 사전은 참고 자료가 아니라 DB 정규 항목/승인 별칭을 기준으로 읽는다. 번역용 TS 사전은 분류 정답으로 사용하지 않는다.
- 다의적 별칭을 하나로 임의 선택하지 않는다. 검토 후보 처리.
- 카테고리 별칭을 전역 검색어 OR로 확장하지 않는다 → 해당 상품에 연결된 분류만 색인한다.
- 관계만 수정하고 색인을 갱신하지 않으면 검색과 탐색이 어긋난다 → dirty 큐 및 명시적 갱신 테스트.
- 사용자 화면과 무관한 계층 확장은 피한다. 기존 N:M/검색 RPC 응답 계약을 유지한다.

## Final Plan
- 사용자 승인: **dev 적용·검증만** (2026-11-16). 운영 DB에는 적용하지 않으며 운영 적용 전 완료/병합 가능으로 표시하지 않는다.
- QA 검토 반영: collector는 저장 전에 DB contract version=2를 확인한다. 실패하면 쓰기 중단.
- v2는 정상 빈 결과와 malformed/unsupported payload를 구분한다. DB에서도 ID·활성 상태·축을 검사하고 실패 시 트랜잭션 롤백한다.
- 미확정 후보는 원문과 이유를 JSON에 보존한다. 별도 dry-run 기본 재해석 명령으로 사전 추가/승인 후 LLM 없이 다시 처리한다.
- status hidden/archived 항목은 자동 확정·정규 검색 색인에서 제외한다. is_hidden은 탐색 노출만 제어하며 검색 의미를 바꾸지 않는다.
- 병합 별칭은 최종 active 항목으로 해석하고 모호한 이름은 보류한다. 부모 시리즈 명칭/별칭도 자식 상품에 색인하며 부모 변경 시 dirty 처리한다.
- dirty 큐 변경 유실을 피하도록 refresh 시 작업 대상 행을 선점·제거한 트랜잭션 안에서 색인을 갱신한다. 이후 concurrent enqueue는 남아야 한다.
- 대표 질의/실제 상품 ID 평가를 기록한다. 순수 단위 테스트만으로 검색 품질 통과를 선언하지 않는다.
- 위 순서대로 collector/DB/검색을 연결한다. 승인 전에는 계획·순수 코드·테스트·읽기 전용 검증까지만 진행한다.
- DB 승인 및 dev/운영 검증이 끝나기 전에는 완료/병합 가능 상태로 보고하지 않는다.
- 코드 커밋, 배포, 대량 LLM 재추출은 자동 수행하지 않는다.

### Remaining risks / follow-up
- 실제 수요 로그 기반 인기 분류 선정과 기존 상품 대량 재분류는 별도 작업이다.
- 기존 데이터 오염 사례: 상품 `4e7c0a13-5d28-467f-b17a-3dfb71904e6d` (MASHLE)의 기존 `name_parts.series.ko`가 `헌터×헌터…(X)`로 저장되어 잘못 검색된다. 이번에는 수동 연결을 보존하고 대량 정리를 하지 않았으므로 별도 근거 검토·정정 필요. 결과 수 증가만으로 전체 분류 품질 통과를 선언하지 않는다.
- Legacy 브랜드 사전 대상 존재 guard는 유지된다. 향후 브랜드 항목을 숨기거나 병합할 때 관련 guard도 함께 검토해야 한다.
- 운영에 v2 RPC가 없으면 새 Collector는 저장 전에 중단한다. 운영 마이그레이션 승인·검증 전 배포 및 main 병합 불가.
